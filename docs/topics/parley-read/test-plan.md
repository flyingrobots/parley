# parley-read — test plan

Evidence lives in `packages/parley-read/test/parley-read.test.ts`, and for the drill-down
(RD-30 to RD-34) in `packages/parley-read/test/open.test.ts`. Cases about the reader rules
build a receipt bundle by hand, byte by byte, because the point of those rules is the bytes a
conforming writer cannot promise; cases about what the loader returns for real output run the
writer (`@flyingrobots/parley-emit`) and load what it left behind.

| ID | Requirement | Spec |

| RD-1 | Both receipt locations for a working directory are located, reported present or absent, and nothing is created or modified to do it | §5, §5.2 |
| RD-2 | Every run under both locations is returned, with its records in `seq` order, and one unreadable receipt file does not lose the others | §1.3, §5 |

| RD-21 | The digest is bounded: it names at most `budget.records` records, and at most `budget.bytes` bytes of line when the budget states them; the records the ranking placed beyond the bound are reported as a count and are in no part of the digest or the answer's records | §9 |

| RD-23 | A copy of a run on the shared history stream may be a projection of the receipt copy: the loader prefers the copy from the source that carries no `parley.history.transform` line for that run, records the other as a projection naming the transform, and attributes a `seq` the projected copy withholds to that transform rather than to an unknown cause | §8, §1.3 |
| RD-30 | A drill-down opens records by `(run, seq)`, the identity a lens names them by, and answers with each one in full, in the order asked, with exactly one outcome per id asked | §1.3, §9 |
| RD-31 | A record stored in a sidecar opens with its contents, the stored bytes checked against the declared `bytes` and `sha256`; a sidecar found missing, mismatched or unchecked is that id's outcome, never a throw and never a claim that the contents are there | §5, §1.2a |
| RD-32 | An id that does not resolve is answered with an explicit outcome naming why — no such run, or no such record in it — and every opened record carries the loader's replay ruling for its bundle, so a record whose bundle is unavailable for replay still opens and says so | §5, §5.4, §2.3 |
| RD-33 | A drill-down is a recorded read: refused without an asker, a view, a window and at least one well-formed id, writing nothing; accepted, it is recorded through the writer as a `parley.query` event that names the ids it opens, read back `validated`, and the record of it is history the next drill-down can open | §9, §2.1, §4.5 |
| RD-34 | Every id a real digest names opens: on receipts a real tool wrote, the `(run, seq)` pairs a `parley.lens` record carries, read back from the read's own receipt, each resolve to the full record | §9, §1.3 |
| RD-50 | Every record a lens names carries a fixed summary beside its `(run, seq)`: the record's `event` and `t` as the loader reports them, and the outcome the ranking established for its run over the whole window. A field the record does not carry usably is absent, never invented, and the summary is part of the line `budget.bytes` bounds | §9, §1.3, §1.2a, §4.5 |
