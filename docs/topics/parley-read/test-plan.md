# parley-read — test plan

Evidence lives in `packages/parley-read/test/parley-read.test.ts`, for the drill-down
(RD-30 to RD-34, RD-60 and RD-74) in `packages/parley-read/test/open.test.ts`, and for exact
numbers (RD-120 to RD-126) in `packages/parley-read/test/exact.test.ts`, whose fixtures are
literal JSON text; RD-124 runs the shared corpus under `conformance/numbers`, and RD-125 runs
`packages/parley-read/test/fixtures/big-tool.ts` as real processes. Cases about the reader rules
build a receipt bundle by hand, byte by byte, because the point of those rules is the bytes a
conforming writer cannot promise; cases about what the loader returns for real output run the
writer (`@flyingrobots/parley-emit`) and load what it left behind.

| RD-32 | An id that does not resolve is answered with an explicit outcome naming why — no such run, or no such record in it — and every opened record carries the loader's replay ruling for its bundle, so a record whose bundle is unavailable for replay still opens and says so | §5, §5.4, §2.3 |
| RD-33 | A drill-down is a recorded read: refused without an asker, a view, a window and at least one well-formed id, writing nothing; accepted, it is recorded through the writer as a `parley.query` event that names the ids it opens, read back `validated`, and the record of it is history the next drill-down can open | §9, §2.1, §4.5 |
| RD-34 | Every id a real digest names opens: on receipts a real tool wrote, the `(run, seq)` pairs a `parley.lens` record carries, read back from the read's own receipt, each resolve to the full record | §9, §1.3 |
| RD-50 | Every record a lens names carries a fixed summary beside its `(run, seq)`: the record's `event` and `t` as the loader reports them, and the outcome the ranking established for its run over the whole window. | RD-60 | The drill-down accepts an optional `budget.bytes`: records open whole, in the order asked, while their summed size fits, and a record past the bound is `over_budget` with its size and no part of its contents; the bound is inclusive, outcomes that return no contents cost nothing, and the budget applied is the one recorded | §9 |
| RD-70 | `budget.ms` is a deadline for the whole read, measured on the read's injectable clock from the call and checked between phases — after the load, after the ranking, and before the digest is written. A read whose elapsed time is past the deadline at a check declines; one at or under it at every check answers; no read answers from a partial load | §9 |
| RD-71 | A read that declines is a recorded run, not a refusal: its `parley.query` is in its receipt, it writes no `parley.lens`, it reports exactly one `parley.error` with code `query.over_budget` carrying `measured`, `limit`, `remedy` and a `detail` stating the bound that declined, the phase, the budget given, what was measured and the budget that would have sufficed where that is known, and it ends with status 2 | §9, §6, §3.4 |
| RD-72 | A `bytes` budget too small even for a digest naming no records declines and states the smallest `bytes` that holds one; that size is exact: a read under it answers and a read one byte under it declines | §9 |
| RD-73 | A read that states no `ms` has no deadline, however long it takes, and a stated `ms` no realistic history reaches is met on the real clock | §9 |
| RD-74 | The drill-down applies the same deadline: `budget.ms` is accepted, recorded in its `parley.query`, checked after the load and after opening, and a drill-down past it declines with the same `query.over_budget` error and opens nothing | §9, §6 |
| RD-80 | A lens states the identity of each run it names once, in a `runs` section, not on every entry: the head's `tool`, `v`, `argv` (already redacted, §5.3) and `inv`, read off the head in the window and nothing else; the run's outcome over the whole window, moved there from the entries; and, when that outcome is `undetermined`, a `reason` from a closed vocabulary. A run whose head is outside the window still has a section, stating `head: "not_in_window"`. Each section is bounded by dropping whole fields, named in `dropped`, never by cutting a string. An `error` or `warning` entry also carries its `code`. All of it counts against `budget.bytes` | §9, §5, §5.3, §2.2, §1.2a, §6, §4.5 |
| RD-90 | A digest folds runs that are the same invocation with the same result: runs whose `inv` is equal and whose outcome, `reason`, `end` status and error and warning codes are all equal are named once, by their most recent run, whose section states `folded: {others, records}` — how many other runs it stands for and how many records of those others the fold left out, both excluding the representative itself (flyingrobots/parley#100), so the section reads as "this run, plus `others` like it"; a run that stands alone has no `folded`. A run with no `inv`, and a redacted run, is never folded. RD-110 adds the result and decision records to what must be equal, the ids to `folded`, and the read that folds nothing. `loss.excluded` still counts every record not named, and `loss.folded` says how many of them the fold, not the budget, left out. The fold is part of how the digest is built, under every view; the ranking still reorders and never filters, and the byte bound still holds exactly | §9, §2.2, §2.3, §1.2a, §5.3 |
| RD-100 | A run section also carries the head's `resolved` (§5): the run's interpretation after defaults and environment, an object of the tool's own shape, copied whole off the head in the window and already redacted there (§5.3), never a subset chosen by key. It is the first field a section drops to fit `RUN_SECTION_BYTES`, whole and named in `dropped`, before `argv`. It counts against `budget.bytes`, and the byte search stays exact with it in the line | §5, §5.3, §9, §4.5 |
| RD-110 | A fold never hides a record that differs among those the window holds (flyingrobots/parley#133; the window's edges are RD-112). Two runs fold only when, beside RD-90's and RD-100's conditions, every result record of theirs in the window is equal: the tool's own records, each `page` and each `sidecar`'s `bytes` and `sha256`, in `seq` order, compared as canonical JSON with the envelope's `t`, `seq` and `run` left out, and from a read's own `lens` its `session` and the `query` it names as well: a tool's own `session` field is compared (flyingrobots/parley#146). The results include a read's own `lens`. Under a view whose surface holds them, the decision records must be equal too: `receipt.step` under `how-it-decided` and `everything`, `cache.hit` under those and `what-ran`. A read that states `fold: false` folds nothing, and its query and lens both say so. A folded section names the runs it stands for in `folded.stands_for`, most recent first, so their records can be opened; the ids are never dropped and are outside the section's bound. `parley.query` and `parley.lens` 1.1.0 carry the new fields, and the reader still validates a 1.0.0 line against the released 1.0.0 schema | §9, §2.2, §2.3, §4.5, §4.6 |
| RD-112 | A fold compares what the window holds, and a run only partly inside it is compared by that part: two runs of one `inv` whose records in the window agree fold even when their receipts differ outside it, and a wider window or `fold: false` shows them apart. A section marks a run the window did not hold whole with `head: "not_in_window"` or with `outcome: "undetermined"` and `reason: "no_end_in_window"`; a run the window shows to have failed carries neither when only its `end` is outside. This is the behaviour `parley.lens` 1.1.0's `runs[].folded` describes; the cases pin it and passed before the description was reworded | §9, §2.3, §1.2a |
| RD-120 | An integer is loaded with the value its text states (flyingrobots/parley#159). The boundary is the safe-integer range, decided from the token: an integer-valued number inside −9007199254740991 to 9007199254740991 is a `number`, however spelt, and one outside it is a `bigint` holding exactly that integer, always, in a receipt line and in a sidecar's contents alike, at any depth. A non-integral number is a `number` only when its decimal value is the decimal value of that number's own JSON serialisation (flyingrobots/parley#173). Copies of one `(run, seq)`, the fold and the canonical comparison compare by value: two different integers never compare equal, an integer equals the same integer written another way, and a number never equals a string of its digits. Loaded and written with `exactJson`, an integer comes out as the digits that went in. Materialisation is bounded: an integer of more than 4096 digits is never built. Every numeric assertion is on emitted text or an independently normalised value, never on a second `JSON.parse` | §1.1, §1.3, §5, §9 |
| RD-121 | A record of a shipped schema that holds such an integer is validated with the integer's exact value, never on a rounded stand-in (flyingrobots/parley#172): its parts that hold no `bigint` by the schema validator, the path to the integer by the reader. One conclusive failure of a constraint is `invalid`, and an unrelated `bigint` hides no required-field, type or ordinary numeric failure; every applicable constraint decided is `validated`; otherwise `partial` with `why: "number_undecided"` and a `record.number_undecided` defect. `anyOf`, `oneOf`, `not` and `if` are three-valued: a failing branch proves nothing by itself. An `end` whose `status` is such an integer is `invalid` under the shipped maximum and, separately, a non-zero status | §4.5, §3.4 |
| RD-122 | A number the reader cannot hold exactly (a non-integral decimal a double does not give back, or an integer of more than 4096 digits) is never returned rounded: the whole line is kept verbatim as a `line.number_unrepresentable` quarantine naming its own run and `seq`, is not a record, and its run never folds; the answer counts such lines, the read reports one `read.number_unrepresentable` warning, and the drill-down says why the id does not open. A sidecar whose contents hold one is `number_unrepresentable`, is not restored, and makes the bundle unavailable for replay. A `seq` beyond the safe range is rejected the same way; a `t` beyond it stays exact in the record, which is undated | §1.1, §1.3, §1.4, §5, §9 |
| RD-123 | Nothing the reader writes or measures throws on such an integer or rounds it: `exactJson`, the writer's and re-exported, serialises a record with the integer's exact unquoted digits; the drill-down's byte bound is measured on that text; and a run section whose head's `resolved` holds one carries it whole and exact on the `parley.lens` line that is written, with the section's size, `digestLine` and the byte budget measured on the text written. `dropped` is for size only (flyingrobots/parley#171) | §9, §5 |
| RD-124 | The reader agrees with the shared numeric corpus, `conformance/numbers`, case for case: an `exact` case loads, from a receipt line and from a sidecar, and `exactJson` of the loaded value is the corpus's text with each number held as the corpus says; an `unrepresentable` case takes the refusal path, with the numbers it names | §1.1, §5 |
| RD-125 | A real tool's integers beyond the safe range, written by the workspace writer in real processes, reach the reader's returned records and its own emitted lines digit for digit; two runs of one invocation whose results are adjacent such integers do not fold; a `bigint` that is a declared secret is redacted and the integers beside it are exact | §5.3, §9, §2.3 |
| RD-126 | What the reader could not compare, it never calls the same (review case 2026-11-25): a run the loader held a line back from never folds however the fold is called, and is unavailable for replay; a `toJSON` on `BigInt.prototype` in the reading process changes neither the fold nor the lens text; the defect for a held-back line is bounded in size | §5.4, §9 |
